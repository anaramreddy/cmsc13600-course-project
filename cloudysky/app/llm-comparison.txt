My data model prioritizes simplicity and directness where the robot-generated one adds extra layers. I use explicit foreign keys on Media (either post or comment) with a database exclusive or check constraint to enforce “exactly one target,” instead of relying on a GenericForeignKey. For moderation, I keep denormalized fields directly on Post and Comment (is_suppressed, suppressed_at, suppressed_reason, suppressed_message_to_author) so views and APIs can filter and render quickly without extra joins. I also store byte counts on posts/comments/media for the dashboard. The result is a smaller, more readable schema that’s easy to migrate and reason about for this assignment.

The robot model is more feature-rich and extensible. It defines SuppressionReason as a separate table and records ModerationAction rows, giving a detailed audit trail of hide/unhide operations and an admin-editable catalog of reasons. It also attaches media with nullable foreign keys to posts or comments, which keeps the schema straightforward but requires care at write time. I appreciate the robot model’s auditability and future flexibility; however, for the current scope, my simplified design is clearer, involves fewer joins, and meets all the requirements.
